**LOGIC AND SOME UI CHANGES TO Issues Data, Issue Page, Cards, and Issues Analytics**

- The automations page is a dead feature, we need to remove everywhere that is had been used e.g. in IssuesData, IssuesCards, IssuePage, MainIssueModal that runs a refetch using the query key, and in links which passes the param type=automation and even the type prop which will now no longer be required. The issue email templates for ReminderTemplate and IssueEmailTemplate also pass a type=issue I guess which is now no longer required. Also its related apis will also need to removed and the corresponding sidebar links also (Both in mobile sidebar and dashboard one). I believe there may be other places I may have forgotten so you'll just make sure its implementation is completely removed.
- Server side pagination for IssuesData which is currently using client side, this will help us eliminate the feature of - load next 50 rows or inputting a number to load more rows since data will now be fetched based on page numbers, next page, and so forth - This feature has been used in Issues Analytics.
- The filters for IssuesData only work on the returned issues, not IssuesCards, just as IssuesAnalytics has a single params and query builder which applies filters to both the cards and data, we can use the same logic here which hooks into both the cards and data for the search filters. That way applying filters refetches returned card counts and data. (In issues data - not the feature which also refetches data when an agent/admin toggles there submissions to view issues submitted by them)
- The search and filter logic for IssuesData (main filter picker, search input field, apply filter button, clear filters (funnel icon), and the refresh button) are currently not grouped together yet they are related, they can be grouped together in a card just like IssuesAnalytics filter panel has done.
- The main issue page for acting on an issue currently depends on returned data from issues data to filter out the particular issue to view, which is not robust, also currently issues analytics data has its own issue view which is view only for all the data and nothing can be acted upon. My recommendation is have one api that fetches the specific issue data, have both the issue link in IssuesAnalytics and issues data point to the same page where an issue can be acted upon. That way agents/admins can act on issues even from the analytics page by routing to that issue - This might require deletion of some routes which will no longer be required after implementation. So basically now, acting on an issue like changing status, priority only optimistically updates the cached data of that returned issue, but issues data and analytics data are invalidated, also the cards query data (This is my view, you can decided on your best recommended approach for this).
- You can create a reusable function for invalidating cache data especially for issues data, analytics data, and there corresponding cards so that performing certain actions that may require data refetch like submitting a new issue, updates, etc. calls that function instead of re-writing query invalidations multiple times - If you think this is a good idea, you can proceed or can advise otherwise.
- Most of these changes have been implemented one way or another for logic surrounding issues analytics feature - You can refer there for anything you might reuse or fork, keeping in mind that separation of concerns is also a consideration here given the nature of some slight differences in logic implementation.
- Any improvement you think is worthwhile along the way (which is not feature-intensive) you can implement/change - Note this could also be a noticed bug. Incase I have left some areas for these implementation changes, you can just proceed and perform the changes.
